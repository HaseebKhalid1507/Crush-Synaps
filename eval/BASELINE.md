# crush v0.1 baseline (crush 2, Phase 0)

What crush v0.1 (`main` @ 28f5d12, release build) does to real and synthetic tool
output, measured in **Claude tokens** as well as bytes. It also measures whether
models can still read the result, and whether it breaks edits. Produced by
`make eval` (see [`README.md`](README.md)). Every number in a marked section is
regenerated by `eval/report.py`. Real-data numbers are aggregates only; per-item
tables are synthetic fixtures.

## Headline findings

1. **On real work crush v0.1 barely runs.** It changed **286 of 59,843** unique real
   tool results (0.48%; 1.5% of those ≥ 2 KiB). That saved **0.21% of bytes and 0.19%
   of tokens** (both tokenizers). Its tool-aware folds (`ls -l`, `ps aux`,
   pipe-format `git log`, JSON arrays) target shapes that are under 6% of what our
   agents read. 70% of the real samples where it fired were `grep` output, hit by
   the generic path-prefix fold.
2. **Bytes overstate tokens, and sometimes have the wrong sign.** `ps aux`: −45% bytes
   but −26% tokens (padding is cheap in tokens). `gh … --json` tabular fold: −11.5%
   bytes but **+11.4% tokens** on the 4.x tokenizer (+4.9% saved on 5.x). CRLF→LF
   strip on a source file: −2.6% bytes, **+0.4% tokens**. All of these pass v0.1's
   byte-based "never enlarge" gate. On the real samples where it fired the gap is
   small (−23.3% bytes vs −21.3% tokens), because prefix folds remove path text,
   and path text is token-dense.
3. **Crushed output is read worse, significantly so for Sonnet.** Strict exact-match,
   thinking off. Raw-vs-raw re-ask noise is 0–4%.
   - Real slice (80 fired samples, 177 questions): **Sonnet 85.3% → 74.0%**
     (30 vs 10 discordant, McNemar p≈0.002); Haiku 80.8% → 79.1% (n.s.).
   - Fixtures (8 fired, 29 questions): Haiku 93% → 66%, Sonnet 93% → 52%.
   - The causes are specific:
     - Path-prefix folding: models give the path without the factored prefix
       (`grep:path` 26/30 → 15/30, even when told to include every directory).
     - 1-char dictionaries in `ls`/`ps`: models return the code (`B`, `A`)
       instead of the value, or misdecode dates (`ls` mtime 4/4 → 0/4).
     - `(×45)` read as "1" or "unknown".
     - JSON→CSV turning `null` into `""`.
4. **It does break edits.** It changed the bytes of **18 real CONTENT outputs**
   (trailing-whitespace strip, blank/duplicate-line collapse, blob elision; 331
   lines no longer verbatim) and 200 real SEARCH outputs. Real `edit` calls copy
   their `old_string` from CONTENT 54% of the time and from **grep output 14%** of
   the time, so SEARCH text must stay byte-exact too.
5. **Where the tokens are** (30 days, unique results, 4.x tokens):
   - CONTENT **51%**
   - SEARCH **18%**
   - UNKNOWN 15%
   - LISTING 5.6%
   - VCS 4.7%
   - LOG 2.8%
   - STRUCTURED 2.7%

   Worker (subagent) transcripts carry **88%** of all tool-result tokens; main
   sessions carry 12%. The 5.x tokenizer (opus-5-5, sonnet-5-5) produces **1.26×**
   the tokens of the 4.x one (sonnet-4-6, haiku-4-5) on the same text, uniformly
   across classes.
6. **CONTENT dedupe has almost nothing to hit on this workload.** Inside a live
   context window, exact repeats are 0.04% of CONTENT bytes. Of `sed -n A,Bp`
   views (22% of CONTENT bytes), only 0.28% re-show lines already on screen.
   Our steered agents don't re-read the way stock Synaps did in the cachebench run.
7. **Fast and robust.**
   - In-process: p50 33 µs / p99 168 µs on real outputs ≥ 2 KiB, max 0.3 ms.
   - Full JSON-RPC round trip: p50 68 µs / p99 0.8 ms.
   - 0 panics over 59,888 inputs, 3,331/3,331 binary responses OK, and library ==
     binary output on every one.

## Method, sample sizes, noise

- **Corpus.** Last 30 days of `~/.synaps-cli/sessions/*.json` (`api_messages`) and
  `~/.synaps-cli/subagent-history/*/sa_*.json` (`history`). `tool_use` is paired
  with `tool_result` by id, and identical outputs are deduplicated. Stored
  transcripts appear to hold only the live context window: older windows are
  rolled out, and the 140 worker `.window-N.md` archives are not parsed. 1,158
  outputs sit at exactly 16,384 bytes (an engine cap), so this is what the model
  *saw*, after capping. In production crush runs before that cap.
- **Classes** come from the first-draft classifier (84% agreement with a 50-sample
  hand audit, below). Class shares carry that error.
- **Tokens.** Anthropic `POST /v1/messages/count_tokens`, authenticated with the
  OAuth access token Synaps already holds (read-only, never refreshed by the
  harness, never logged). It is counted with two models, one per tokenizer
  family: `claude-sonnet-4-6` (4.x) and `claude-opus-5-5` (5.x).
  - Per-sample counts cover all 45 fixtures and all 286 fired real samples, raw
    and crushed.
  - Class totals for the whole corpus are counted in packed batches. Batching
    error, measured on 150 samples, is +0.07%.
  - ≈3,050 count_tokens requests, all cached by content hash.
- **Accuracy.** Questions with exact answers are generated from the RAW output:
  - grep file/line/count
  - `ls` size/perms/mtime/owner/symlink
  - `ps` fields
  - test pass/fail and counts
  - compiler diagnostic locations
  - git author/email/subject/date
  - JSON field-by-id, null-vs-"", length
  - run counts and adjacent lines

  They are asked about RAW and about CRUSHED (crush's exact replacement, header
  included) in separate fresh `synaps rpc` sessions, through an isolated base
  dir with all tools disabled and thinking off. Models: `claude-haiku-4-5` and
  `claude-sonnet-4-6`.
  - A seeded 25% of samples get a second RAW ask, which gives the noise floor.
  - Questions that quote a line no longer present verbatim in the crushed text
    are dropped as unfair.
  - grep path questions ask for "the path as grep reported it, including every
    directory component". A first wording ("exactly as it appears") was biased
    against crushed; those samples were re-asked and merged.
  - Strict scoring is primary. "Lenient" also accepts an answer line that
    contains the expected value, because Sonnet often decodes crush's
    dictionaries out loud instead of answering.
  - Real slice: 80 of 283 fired samples with questions, stratified by class ×
    transform.
- **Spend.** 508 model calls in total ($4.90 at list price):
  - an 11-call smoke run ($0.36);
  - a 382-call main run;
  - a 115-call SEARCH + new-fixture re-ask, merged (main + re-ask: $4.54).

  The per-run cap is 400 (`--max-calls`).
- **Not covered here:** thinking-on accuracy (real sessions run with thinking;
  this is the harsher setting), multi-turn task success (cachebench Scenario A,
  Phase 4), and the 5.x models for accuracy.

## 9. Recommendations for Phase 1, ranked by real token mass

Shares are of 4.x tokens over 30 days of unique tool results.

1. **CONTENT, 51%: make it untouchable, and don't count on crush for savings.**
   - Phase 1's classifier must route CONTENT to "no byte changes". Gate on a
     byte-identity property test, plus `edit_safety.py --strict` on the corpus.
     v0.1 fails both: rstrip, blank and duplicate collapse, CRLF, blob elision.
   - The dedupe lever is ~0.3% here, so CONTENT savings have to come from
     elsewhere: spill/virtualisation of huge views, narrower reads via prompt
     steering, rollover compression. Not from crush transforms.
2. **SEARCH, 18% (9.0M tokens): the biggest compressible class.**
   - v0.1's prefix fold already shows the token win (−38% on absolute-path grep),
     and the accuracy cost: models drop the factored prefix.
   - The Phase 2 group-by-file transform must write each file's **full path** as
     its group header. No shared-prefix factoring, no relative remainders.
   - Keep `line:text` byte-exact: 14% of real edits quote grep text.
   - Gate on `grep:path` / `grep:most` parity.
3. **UNKNOWN, 15% (7.6M): shrink it before transforming it.**
   - Phase 1 classifier work should look inside for-loops and `python3 -`
     heredocs (≈7 MB together), send `cat *.log` and `tail` of logs to LOG, and
     treat `forum_read` (3.4 MB) and web fetches as prose.
   - Only the generic safe transforms belong here.
4. **LISTING, 5.6% (2.8M): keep the column factoring, drop the 1-char dictionaries.**
   - The token win is real (`ls` −29…41%, `ps` −26%).
   - The dictionaries are what break reading.
   - Lift the 62-value cliff.
   - Re-measure tokens without dictionaries, since part of the win may go with them.
5. **VCS, 4.7% (2.4M):** v0.1 does nothing on real VCS output; the pipe-format
   `git log` it targets is rare. Long → short `git status` and compact default
   `git log` are next. Both need accuracy gates (author/subject/date questions
   exist).
6. **LOG, 2.8% (1.4M) here; likely bigger for other users.** Our sessions
   under-run builds and tests, and the fixtures show the shape: 160 passing test
   lines, 100+ repeated warnings. Collapse passing tests, but write counts in
   words, not `(×N)`: models read `(×45)` as 1 or unknown. Keep failures
   verbatim.
7. **STRUCTURED, 2.7% (1.4M):** prefer lossless minify. Fold arrays to CSV only
   when it is **token**-negative on the tokenizer in use, and never when it erases
   `null` vs `""`.

Cross-cutting, for Phase 1's framework:

- Measure and gate in **tokens**, on the 5.x tokenizer the user runs. The
  "never larger" invariant must be token-based: v0.1 outputs grew in tokens while
  shrinking in bytes on 1 (4.x) / 2 (5.x) real samples and on 2 fixtures.
- Count the provenance header (~15–20 tokens) against the win.
- **Expected impact, honestly.** If every non-CONTENT class got the best
  per-class token saving seen here (SEARCH ~35%, LISTING ~30%, LOG ~50%,
  STRUCTURED/VCS ~20%, UNKNOWN ~5%), tool-result tokens would fall by about
  **11–12%**, all of it at accuracy parity, which v0.1 doesn't reach. That is
  below the plan's 15–30% guess, because half the mass is CONTENT and CONTENT
  barely repeats.
