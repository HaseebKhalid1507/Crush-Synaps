# crush 2 — Phase 1 gate results

crush-core (classifier, transform framework, invariants, generic transforms, SEARCH
grouping) measured on 30 days of real tool results (59,843 unique, private, never
committed) and 50 synthetic fixtures. Everything between `BEGIN`/`END` markers is
regenerated by `eval/report.py` (`make eval` / `make gate`); real-data numbers are
aggregates only. Method and harness: [`README.md`](README.md); v0.1 for comparison:
[`BASELINE.md`](BASELINE.md).

## Headline

- **What ships enabled saves almost nothing on this workload, by design.** The
  default config fires on 85 of 59,843 real results (0.14%): identical-line runs,
  `\r` progress redraws and base64 blobs are rare in our sessions. Every one of
  those passed accuracy parity, none grew in real tokens, CONTENT was never touched.
- **SEARCH grouping is built, measured, and disabled.** It fires on 3,413 real
  grep outputs, saves ~20% of their tokens (≈3.5% of all SEARCH tokens, 0.6% of all
  tool-result tokens), rebuilds every line byte for byte, and **fails accuracy
  parity**: hits separated from their path were attributed to the wrong file, line
  or count more often (Sonnet 81.2% → 76.2%, Haiku 75.1% → 68.5%; pooled McNemar
  p ≈ 0.01). Per the gate it ships off; `eval/configs/search_on.json` keeps it
  measured on every `make eval`.
- **The classifier is the bigger Phase 1 win.** Hand-audit agreement 84% → 94%;
  UNKNOWN falls from 14% to 7.6% of bytes, mostly into PROSE (forum, memory,
  worker reports, web pages: 5%) and LOG (`cat *.log`, loops, test runs behind
  `python3` heredocs).
- **The gate holds in code.** 0 panics, 0 non-idempotent results, 0 CONTENT
  changes, 0 SEARCH rebuild failures, 0 results with more real tokens, crush-ext ==
  library on every request, corpus p99 0.08 ms, every 256 KiB worst case under 1 ms.

## 3. Accuracy: raw vs crushed

Strict exact-match, thinking off, fresh `synaps rpc` session per ask, isolated
`SYNAPS_BASE_DIR` + `HOME`, access-token-only auth, the real `auth.json` hashed
before and after. Run on the candidate config (every transform on), so the
disabled transform was tested in the same run. A transform ships only if **both**
models are at parity: McNemar p ≥ 0.05 **and** its raw-only excess
((raw-only − crushed-only) / questions) is within that model's raw-vs-raw
disagreement on re-asked questions.
<!-- BEGIN:accuracy -->
<!-- END:accuracy -->

What went wrong for SEARCH grouping (discordant answers, read by hand): the model
attributes a hit to a neighbouring heading (`src/serve/engine.rs` for
`src/serve.rs`), reads the line number of an adjacent hit, or miscounts a group.
The drop is spread evenly over small and large outputs (≤ 20 hits, 21–60, > 60;
≤ 3 files, 4–10, > 10), so no size threshold rescues it. Phase 2 should test
layouts that keep the path on (or next to) every hit line while still removing
repetition, before trying grouping again.

## 7. Token estimator and the SEARCH layout choice
<!-- BEGIN:estimator -->
<!-- END:estimator -->

The estimator is a non-negative linear model over 16 one-pass shape features
(word pieces, long-word excess, camel humps, digit runs, punctuation runs,
indentation, newlines, non-ASCII, letter/digit switches). Its error on whole
texts is what matters for telemetry; the gate only needs the *sign and size of
the change*, checked under both families with a margin (≥ 8 tokens and ≥ 2%), and
every fired corpus result was re-counted with the real tokenizer above.
